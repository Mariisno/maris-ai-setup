# Domain: Hobby — an example for personal projects

| | |
|---|---|
| **Lead** | LOLA · inbox `<LOLA_INBOX_DIR>/LOLA.md` |
| **Board** | none |
| **Repositories** | personal repositories under `$HOME/code/private` (example) |
| **Briefing (notes)** | the personal projects note in the notes folder |

## Who owns what
- **The human** gives free rein on the creative side: deliver something charming and
  finished, not a list of questions about details.
- **Nothing from work** in here: no work repositories, issues, boards, names or customer
  content, and never a work account. The line is drawn by *where the thing lives*, not by
  whether it would help at work.
- Personal git identity. Push to private repositories is fine when the human has said so
  once; public repositories, new repositories and deploys still need a yes each time. Never
  merge the default branch without being asked (a standing yes, if the human gives one, is
  written here on its own line: the lead skill's `references/autonomy.md` has the form and
  the conditions). No new packages without a yes.
- **No unannounced sound** or visible windows from a specialist. Everything is off by
  default; play only what the human asked for.
- Two specialists never write in the same working tree: give each its own worktree.

## Overrides the role files
- Work-specific skills and tools (a company design system, a company tracker skill) are not
  used here, even when a role file names them. Use the general check instead: Nielsen,
  WCAG 2.2 AA, empty and error states, an undo path, consistency, and `microcopy` for text.
- Nothing that costs money. Everything through a pull request. Every merge, deploy, config
  change and deletion gets a line in the project's change log (what · where · before → after
  · how to undo).
